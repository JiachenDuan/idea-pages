FAQ

What access do you need?
Best case: a read-only view of relevant repos + logs + queue metrics. No production credentials. All changes go through your normal PR/review process.
What stacks do you support?
We start with a narrow set to stay fast: Node/Python services, Postgres, and a queue like SQS/Redis/RabbitMQ. If you’re outside this, we can still scope it on the fit call.
How do replays avoid double-charging or double-provisioning?
We implement idempotency keys + dedupe storage, and we put replay behind guardrails (batch limits, dry-run where possible, and explicit approvals).
How long do you retain data/artifacts?
You choose. By default we keep only what’s needed for active work; we can operate with a time-boxed retention window and delete on request.
What do we need to have in place before onboarding?
A repo we can PR into, an owner for approvals, and a place to send alerts (Slack/email). If you already have a queue, great — if not, we’ll propose the smallest reliable option.
We don’t invent business events or rewrite your product. This is a reliability layer + runbook so your existing webhook-driven workflows stay correct.
